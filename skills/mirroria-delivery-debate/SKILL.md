# Mirroria 交付辩论

## Overview

把多智能体讨论变成“唯一执行者写入 → 反方审查证据 → 原执行者修复 → 协调者验收”的交付闭环。最终目标是用户要求的真实文件、代码或结论，而不是更多讨论文本。

详细的角色消息结构和状态机见 [references/protocol.md](references/protocol.md)。

## 1. 先判断任务模式

普通低风险概念问题不进入本技能，直接回答；不得为了套流程启动文件执行者或辩论。若任务确实触发本技能，选择最轻的足够模式：

- `quick`：两种不开辩论的路径：无需改文件且无需反方审查时，由回答者产生答案并按验收标准自检；很小的单文件改动则由一个本地执行者完成并自证。
- `plan`：目标含糊或存在高风险写入。先输出最多 7 条可验证计划，再进入 `act`；清晰且可机械验证的多模块修改不必仅因文件多而进入计划模式，计划也不能代替执行。
- `act`：默认模式。唯一执行者直接工作，审查者只在产物形成后介入。
- `debate`：高风险结论、复杂代码、研究审稿，或用户明确要求对抗审查。采用本技能的完整闭环。

不要要求用户写长提示词。根据任务和工作区自动推导模式、文件范围与验收条件；只有会显著改变结果的缺失选择才询问用户。

## 2. 锁定用户意图

协调者先做最小只读勘察，再生成一份短契约。目标、验收含义和用户约束锁定；若勘察后才发现具体文件范围，只能用新的勘察证据把目录或模式范围细化为确切文件列表，并公开记录 `contract.amended`。不得偷换目标、改变验收含义、增加用户未要求的交付物或放宽约束：

- `goal`：用户最终要得到什么。
- `deliverables`：应存在或应修改的文件/结果；从用户原话推导，不虚构额外交付物。
- `acceptance`：可直接核验的标准。
- `workspace`：允许操作的目录。
- `constraints`：只包含用户明确要求和真实安全边界。

若用户要求“修复/生成/修改”，契约必须标记 `requires_file_changes=true`。当前 Mirroria 的 `ask` 权限模式是只读预览：执行者只能勘察并给出精确改动方案，不能声称已经交付；协调者必须提示用户改用 `auto`（仅限所选工作区）或 `full` 后重跑。只有 `auto` / `full` 才能把文件任务交给有本地工具能力的执行者真正修改与验证。

## 3. 指派唯一执行者

- 选择能读取、编辑并验证目标工作区的本地执行器。纯 API 模型不能承担本地文件写入的主执行角色。
- 同一轮只能有一个写入拥有者。其他模型做研究、复核或反方审查，不并发改同一批文件。
- 执行者必须先检查现有文件和规则，再修改；不得只写建议书冒充交付。
- 连接断开时保留上下文和已完成证据，按退避策略重连；仍失败则切换另一个具备相同文件能力的执行器。

执行者对外汇报公开进度：正在读什么、改什么、运行什么、等待什么、重连次数和耗时。不要暴露私密思维链，也不要用每十秒一条重复心跳淹没时间线。

## 4. 形成证据包

执行者提交给审查者的不是结论性宣言，而是最小证据包：

- 改动文件的绝对路径及内容证据（必须提供 diff 或内容 hash；mtime 只能作为新鲜度辅助信息，不能证明改动）。
- 关键修改的简短说明。
- 实际运行的验证命令、退出码和必要输出。
- 对应每条验收标准的证据引用。
- 尚未验证的事实和外部阻塞。

文件不存在、无法用 diff 或内容 hash 证明所需改动、命令未运行、执行器自述“没有修改”时，不得声称完成。链接应指向真实的绝对文件路径，并可由宿主应用打开。

## 5. 进行反方审查

审查者默认站在反方，但必须攻击可验证的缺陷，而不是为了反对而反对：

- 逐条检查锁定的验收标准。
- 优先检查真实产物、diff 或内容 hash 与测试；时间戳和文字自述不是改动证据。
- 对每个阻断项给出 `claim`、`evidence`、`required_fix`。
- 不添加用户未要求的验收门槛，不重复已经解决的异议，不讨论与交付无关的话题。
- 输出 `ACCEPT` 或 `BLOCK`。只有影响用户结果的缺陷可以 `BLOCK`。

`BLOCK` 后必须把具体修复单退回原执行者。执行者修改实际产物并提交增量证据；审查者只复查变化部分和受影响的旧证据。

## 6. 控制讨论收敛

- 同一事实不得在没有新证据时来回争论。
- 连续一轮没有文件、证据或判定变化时，协调者必须停止空转并重新指派执行动作。
- 同一阻断项最多经历两次有实质改动的修复循环；超过后协调者只能用新证据判定异议无效/越界，或重新指派执行者、明确标记真实阻塞。仍然有效的 `BLOCK` 绝不能被投票覆盖。
- 下一轮只传递契约、最新产物摘要、尚未解决的异议和证据增量，避免重复整段上下文。
- 一旦所有验收标准有证据且审查者 `ACCEPT`，立即停止，不为凑轮数继续讨论。

## 7. 完成状态门禁

先按契约类型选择门禁：

- 文件交付（`requires_file_changes=true`）：要求的产物存在，diff 或内容 hash 证明要求的文件改动确实发生，验收命令成功，且审查者给出 `ACCEPT`；`quick` 单文件修改则由协调者完成等价证据核验。
- 仅回答 `quick`（`requires_file_changes=false`）：答案已产生，每条验收标准有答案内容、来源、计算或其他合适证据，协调者完成自检。不要要求 `artifact.changed`、`changed_files`、文件链接或不相干的命令。
- 无文件的高风险结论或用户明确要求的对抗审查：每条验收标准有结论证据，且审查者给出 `ACCEPT`。

上述对应门禁满足后，还必须同时满足：

- 所有要求的验收动作成功，或已明确说明某类命令不适用的原因。
- 最终文本没有 `BLOCKED`、`CONSENSUS:BLOCK`、`未交付`、`没有产生新文件` 等失败信号。

否则：可恢复问题回到执行步骤；不可恢复的真实外部阻塞标记 `run.blocked` 或 `run.failed`。绝不把失败说明包装成“最终交付”。

## 8. 面向用户的最终交付

最终回复先给结果，再给最少必要证据：

1. 完成了什么。
2. 文件交付时，给可点击的真实文件链接或工作区路径；仅回答时省略。
3. 给出实际运行的关键验证及结果；仅回答时只提供必要的来源或计算，不制造工具仪式。
4. 仍存在的真实风险（若无则不制造风险清单）。

不要输出角色内部 JSON、整段辩论记录或官样状态报告。用户应能用很短的提示词得到可打开、可复核的交付物。
